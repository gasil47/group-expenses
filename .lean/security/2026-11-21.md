# Security review — 2026-11-21 — e4760d7..HEAD (23e93df)
Audit: 0 dependency advisories; 2 MAJOR "hard-coded credential" hits are false positives (placeholder apiKey in js/config.js:4; a password-field type toggle in js/views/signin.js:22).
## Findings
- MINOR firestore.rules:105-111 — invites never expire and cannot be revoked or rotated; no way to remove a member (groups update only allows `name`/self-join). A leaked link gives permanent read/write on the group's finances → add a revocable invite (e.g. `active` flag checked in onlyAddsSelf, creator-only update) · Prove: rules test where a revoked invite's join is denied.
- MINOR firestore.rules:62-77 — expense `description`, `spentOn`, `shares` values and history `before`/`after` are not type- or size-checked (only keys, amountFils, paidBy). A member can store negative/non-numeric shares or ~1 MiB strings and break every member's balances view (spec R1 accepts wrong sums; non-numeric/oversize is a separate, cheaper break) → validate `description is string && size()<=200`, `spentOn is string && size()==10`, `amountFils < 1e10` · Prove: rules test that a 5000-char description and a non-string spentOn are denied.
- MINOR firestore.rules:35-37 (onlyAddsSelf) and :89-94 (create group) — joiner's `memberNames[uid]` and the creator's `memberNames`/`inviteToken` are only `is string`, unbounded and unchecked → `validName(.., 60)` · Prove: join with a 10k-char name is denied.
- MINOR firestore.rules:97-110 — settlements: either party may record a payment unilaterally (spec A6), so a payer can reduce their own debt with no consent, and no entry is ever reversible (update/delete false, no history). `deleted` is client-supplied and not forced false → require `deleted == false` and add a reversal/dispute path if trust matters · Prove: create with `deleted: true` is denied.
- MINOR firestore.rules:114-119 — any member can create unlimited invite docs (no key restriction, no count limit) → restrict `keys().hasOnly(['groupId'])`; consider App Check against hostile signed-in accounts · Prove: invite with extra keys denied.
- MINOR index.html / firebase.json — no hosting config, so no CSP or security headers (frame-ancestors, X-Content-Type-Options); the Firebase SDK is a dynamic import from gstatic with no SRI (not possible for dynamic import) → add a `hosting.headers` CSP restricting script-src to self + www.gstatic.com when deploying · Prove: header present in deployed response.
## Checked, no issues
- Trust boundaries: every write path is rules-enforced; updatedBy/changedBy/createdBy == auth.uid, timestamps == request.time (no client time trusted); paid/from/to must be members; expense + history written atomically with matching action/deleted; history and settlements immutable; expenses no hard delete.
- Access rules: deny by default; non-members cannot get/list groups, expenses, history, settlements; invites cannot be listed; users/{uid} is owner-only.
- Join: only own uid appended, memberNames diff limited to own uid, token must resolve to this group's invite (tested, test/rules.spec.mjs).
- Invite tokens: 32 chars of a 36-char alphabet from crypto.getRandomValues (~165 bits, js/routes.js randomToken); enumeration infeasible.
- Client rendering: no innerHTML/insertAdjacentHTML anywhere; DOM built via h() with textContent; WhatsApp link uses rel=noopener and encodeURIComponent; hash route tokens are only used as Firestore doc ids.
- Secrets/config: js/config.js holds placeholders only (Firebase web config is public by design); no service keys or .env tracked; firestore-debug.log is gitignored and untracked; emulator ports are local only.
- Dependencies: audit reports 0 production advisories.
